# Обмен офлайн-программы и CRM

Исходная проверенная программа сохранена без изменений: `C:/Users/Izop300520251/Documents/Codex/2026-10-27/x20/outputs/exhibition-app`, архив `kosmoport-v1.0.0-windows.zip` рядом. SQLite schema user_version=1, Node 24. Никакие рабочие базы адаптер не меняет.

1. На офлайн-ноутбуке скачайте SQLite резервную копию через программу. Остановите приём на время сверки и переноса. Не копируйте только SQLite-файл из работающей WAL-базы.
2. Вложенным `runtime/node.exe` запустите `export-snapshot.mjs backup.sqlite NEW-snapshot.json`. Вход открывается readOnly, существующий выход не перезаписывается. Файл содержит номера всех билетов и внутренние данные: передавайте только сотрудникам.
3. Войдите в CRM через браузер как manager/admin/owner. Отправьте JSON в `POST tickets/import` с CSRF. Формат `kosmoport.tickets`, version=1. Обычный внешний API InfinityFree не используется.
   При размере больше 1 МиБ сначала выполните `runtime/node.exe split-snapshot.mjs NEW-snapshot.json NEW-folder`. Импортируйте пронумерованные файлы по порядку; каждый меньше 800 КБ. Точки идут перед партиями, партии перед билетами; активный проход находится в том же файле, что билет. Все операции входа держите остановленными до завершения всей последовательности. Каждый запрос атомарен, вся последовательность — нет. На первом конфликте остановитесь, не пропускайте файл и не продолжайте приём на частично перенесённой базе.
4. Совпадающие записи пропускаются. Отличающиеся ID/состояния возвращают 409 `import_conflict` и список conflicts; весь импорт откатывается. Это намеренно не автоматическая синхронизация и не стратегия «последняя запись побеждает». Сохраните обе копии и сверяйте расхождения до продолжения учёта.
5. `GET tickets/export` возвращает такой же versioned snapshot для архива/переноса CRM. Обратное автоматическое применение в офлайн SQLite не реализовано: не подменяйте им базу и не обещайте двустороннюю синхронизацию.

Сохраняются source.id, batch.id, ticket.code, event.id, admission.id, legacy metadata источников и аудит. Источник — точка распространения, не адрес посетителя. PIN и прочие секреты settings не экспортируются. print_config партии фиксируется в snapshot; если ещё не печатали, используются текущие реквизиты, чтобы сохранить ограничения дат.

Старый журнал отмен содержит лишь code/time без admission id. Адаптер связывает отмену с предшествующим проходом; для неразрешимой истории ставит `legacy_reversal_inferred`. Активный проход без совпадающего события отклоняется. Исторические офлайн-проходы имеют manual_adult_payment_confirmed=null: нельзя задним числом доказать факт подтверждения. Fiscal verification везде false.

Не используйте два независимых места приёма одновременно: JSON обмен не даёт глобальную защиту от дубля между офлайн-кассой и CRM. Выберите одну активную базу, остановите её перед переключением и сверяйте экспорт. Внутри CRM операции атомарны; общий InnoDB lock сериализует импорт, проход и отмену. Рекомендуется небольшой тираж на импорт; верхняя граница коллекции 100000, HTTP лимиты хостинга/ядра могут быть ниже. Большие снимки требуют отдельной согласованной пакетной процедуры, не обрезайте их вручную.
